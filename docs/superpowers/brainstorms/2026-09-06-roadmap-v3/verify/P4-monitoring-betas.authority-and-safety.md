## Refutations

### A-1 (amend) — The "T1 automations" cannot be reached by the kill switch that exists on `main`; env-var flags are not §16's switch; E3-M1 and E3-M3 have none at all
- **Claim under test:** E1 Tier "the proposal is a **T1 automation**"; E3 Tier "recall and survey = **T1 automations** (Recall & Follow-up scope, SPEC:784)"; E4 Tier "**T1**". Switches named: `VITALS_BASELINE_PROPOSALS_ENABLED` (E1-M3), `TRAJECTORY_WATCHER_ENABLED` (E4-M3). None for E3-M1's recall task or E3-M3's "+30 d the recall automation opens a structured call task".
- **What §16 obliges:** SPEC:780 — automations are "deterministic jobs … running under the agent harness (identity, kill switch, heartbeat, mode/backfill gates, tier)"; SPEC:789 — "**per-agent kill switch**, instant, itself evented · … **global halt (v4.6)** — one flag pauses every agent and automation, itself evented".
- **What exists:** one column, `agents.kill_switch` (`apps/core/src/kernel/db/schema/auth.ts:97`); one writer, `setKillSwitch` (`kernel/auth/agents.ts:25-27`); one enforcement point, `kernel/auth/guards.ts:51` `if (agent.killSwitch) throw new ForbiddenException(...)` — inside the HTTP guard, for a caller presenting `x-agent-key` (`guards.ts:47-53`). No global halt: `git grep -i -E "globalhalt|global_halt|agents_halted|AGENTS_ENABLED"` over `apps/core/src` returns only the agent-key rows above. Scheduler jobs are in-process registrations over a direct `db` (`kernel/worker/jobs.ts:338-344`, the very `rollupUserDayFacts` pattern E1-M1 cites) with a heartbeat row and `sweep.failed` (`kernel/worker/scheduler.ts:9-16`) and **no runtime disable** — the only enable is config-time (`jobs.ts:308,351` `enabled: intervals.retentionEnabled`).
- **Consequence:** three new automations would run as sweeps that neither `agents.kill_switch` nor any halt can stop; an env var needs a restart and appends no event, so it is neither "instant" nor "itself evented"; the recall and survey automations — the ones that contact a patient — have no switch of any kind. Every existing sweep on `main` (`jobs.ts:9-23`) shares the gap, but P4 is the first to call its sweeps "T1 automations" in a phase doc and thereby claim §16's protections.
- **Amendment:** (a) name them what the codebase names them — module sweeps under the scheduler — and give each a DB-held switch (an `opd_config` / definition row) whose flip appends an event; or (b) keep the T1 framing and run each under an agent identity so `guards.ts:51` reaches it. Either way E3-M1 and E3-M3 get a switch, and the phase doc states in one line that no automation on `main` runs under a global halt today.

### A-2 (amend) — The T1 proposal is designed to live in the table the board consults, and no mutant forbids the board from reading a proposal row
- **Claim under test:** E1 Build (2) "migration `patient_vitals_baselines(patient_id, param, low, high, reason, ordered_by/at, valid_until, **source doctor_order|proposal**, superseded_by, cancelled_by/at)`"; (3) "a pure `boardFlags(flags, order)` consulted ONLY by `dangerOf`"; (6) "T1 proposal … batched to the cockpit, never the bay"; edge row 7 "the nurse proposes from the history tab". E1-M2's mutants: "an order widens `dangerFlags`" and "order suppresses all"; E1-M3's: "lapsed order still consulted".
- **What is missing:** nothing states that `boardFlags` consults only rows with `ordered_by` = a holder of `opd.vitals.baseline.order` and `source = doctor_order`. A row written by the nightly job (or by a nurse from the history tab, row 7) with `source = proposal` and the same `low/high` columns is, by the table's own shape, an `order` unless something filters it — and no mutant asks.
- **Why it is an authority breach, not a bug:** a machine-written row that suppresses a board bump is the T1 automation acting alone on a clinical safety decision — T3/T4 by SPEC:778's ladder, and the exact act `escalation.ts:26-33` reserves for the double-confirmed danger case ("the single case in the entire seat where the agent acts alone"). SPEC:789's "API-only, never the database" is written for this: an automation must not be able to write what the safety path reads.
- **Amendment:** the proposal is an EVENT (`vitals.baseline_proposed {patientId, param, low, high, readingIds, rule_version, constants}`) rendered in the cockpit batch, never a row in `patient_vitals_baselines`; a doctor who accepts it creates the order through the ordering API with `source: proposal` + the proposal's event id as provenance. Add the mutant to E1-M2/M3: "a proposal row (or an order row with `ordered_by` null) suppresses the bump → red". Stamp `rule_version` and the constants snapshot on the proposal — E4-M3 does this for `off_trajectory`; E1-M3 lists `readingIds` only, so the signed order cannot prove which arithmetic proposed it once the DTC revises k (DECIDED 4).
