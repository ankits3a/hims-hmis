## R1 — KILL (the acceptance line, not the goal): E7-M3 / edge 1 prove the guard by executing `deploy.sh` under jest with the guard deleted — the 12:35 mechanism

**Claim in the design.** E7-M3: "`deploy.sh` under `JEST_WORKER_ID` exits non-zero **with the guard deleted** (fail-first, then the mutant)"; edge 1: "refuses under `JEST_WORKER_ID`/`NODE_ENV=test`, **independent of any deletable guard** … fail-first test in `deploy-parity`; the mutant (guard deleted) still refuses".

**Refutation.**
- A guard inside `deploy.sh` is by definition deletable; "still refuses with the guard deleted" is only true if the test EXECUTES the script and something else stops it. The incident memory records exactly this shape: the test ran `spawnSync("bash", [DEPLOY_SH], …)`, the mutant deleted the guard, and `DEPLOY_DIR` defaulted to production — "production's images rebuilt from a lane tree, 22 migrations applied, nine containers restarted. Killed nothing, noticed as an 88-second test" (`memory:deploy-sh-executed-by-a-test:13-25`). The default is still there: `DEPLOY_DIR="${HMIS_DEPLOY_DIR:-/opt/hmis-prod}"` (`docker/prod/deploy.sh:44`).
- `deploy-parity` is **static**: "They are static — they read the SHIPPED BYTES of `deploy.sh` — because the failure is an ORDERING between programs a jest run cannot execute" (`apps/core/test/deploy-parity.test.ts:353-355`). A static leg can assert the guard's text is present; it cannot show a mutant "still refuses". So the criterion as written forces an executing leg.
- The proposed guard key is trivially absent in the incident's own shape: a test that spawns with an explicit `env:` carries no `JEST_WORKER_ID`; the guard never fires and the deploy runs. The classifier does not see a spawn inside jest ("what the classifier sees is `jest`", memory `:36-38`).
- The memory's rule is the opposite of the design's: "a test that EXECUTES a guarded script must be unable to reach anything real, **independently of the guard** … make the answer 'nothing' by construction" (`:11-12, :52-54`). Independence has to live in the TEST HARNESS (env), not in the script.

**Amend.** E7-M3 acceptance becomes: (a) a static-bytes leg in `deploy-parity` asserting the refusal text exists (fail-first by deleting it); (b) any executing leg sets `HMIS_DEPLOY_DIR=<nonexistent>` AND prepends a stub `docker` (exit 99) to `PATH` on every leg, so a mutant with every guard deleted does nothing by construction; (c) one sentence in the milestone: "a mutation run that spawns `deploy.sh` without (b) is itself the defect". Edge 1's expected behaviour: "the test cannot reach the daemon, whatever the script does".

## R2 — AMEND (safety): "never an agent's act" (edge 25) has no mechanism; production and UAT share one script on one box, and the orchestrator runs it routinely

**Evidence.**
- Production deploys and UAT deploys are the same `deploy.sh`, distinguished by `HMIS_TARGET=uat` (`origin/lane/commissioning-t3`); 11i D8: "UAT is deployed by the orchestrator after every green train batch … production is deployed weekly by the owner's hand" (`docs/superpowers/plans/2026-09-06-phase1-11i-the-stand-up-path.md:160-161`). The orchestrator is an AI session.
- `origin/main`'s `deploy.sh` has **no `HMIS_TARGET` at all** today (grep of `origin/main:docker/prod/deploy.sh` for `HMIS_TARGET|uat`: only comments at :662, :816; T3 is #120, still open). Memory mistake #1 was precisely an agent running "`HMIS_TARGET=uat … deploy.sh` from a worktree … whose `deploy.sh` predates the target concept — so `HMIS_TARGET` was an environment variable nothing read and `DEPLOY_DIR` defaulted to production" (`memory:deploy-sh-executed-by-a-test:29-33`).
- The refusals on the build path (dirty tree, `HEAD != origin/main`, `deploy.sh:67-75`) are satisfied by any lane rebased to `origin/main` with a clean tree — the normal state before a PR. The classifier "blocks two things … writing to the production database by hand, and launching the deploy via `setsid nohup`. **The deploy runs fine through the harness's own `run_in_background`**" (`memory:prod-deploy-state:22-24`). An agent can deploy production from its Bash tool today.
- P6's only new guard (E7-M3) keys on `JEST_WORKER_ID`/`NODE_ENV=test` — one wrapper. The memory: "Test execution is a hole in every command-level guard" (`:38`); so is `pnpm`, `tools/*.sh`, cron.

**Amend.** Add to E7-M3 a POSITIVE owner-hand requirement on the prod target, wrapper-independent: refuse unless stdin is a TTY (`[ -t 0 ]`), `HMIS_DEPLOY_OPERATOR=<name>` is set, and the operator types the target short SHA at a prompt; UAT is exempt. Every agent invocation (Bash tool, jest, cron, `setsid`, `run_in_background`) is non-interactive and refuses on prod regardless of which wrapper hid it. Record the operator name in the `log/deploy-<sha>.json` E7-M1 already proposes. Edge 25 then has an artefact ("the refusal transcript") instead of a norm.

## R3 — AMEND (a fact the owner holds + a law register, marked DECIDED): DECIDED 5 / E5-M1 seed five invented devices on production

**Claim.** DECIDED 5: "`seed-radiology` joins `deploy.sh` for the Class-C rows (study types without prices, **device resources**)"; E5-M1 acceptance: "`radiology_study_types_active`, `radiology_device_present` ok after the next deploy".

**Refutation.**
- The seed writes a CONSTANT of five machines — `XR-1`, `USG-1`, `CT-1`, `MRI-1`, `MMG-1` — on the reasoning "The owner's standing rule permits assuming standard machinery" (`apps/core/scripts/seed-radiology.ts:50-53, 69-75`). That is a design assumption, not the hospital's inventory. Three of the five are ionising.
- RM's G3 row says device rows are master data entered "by the department head, through the module's screens — **never a seed** on production" (`docs/superpowers/2026-09-06-ROADMAP-v2.md:361`). RM rule 2 (`:372-374`) covers Class C *definitions*, not resources; "device resources = Class C rows" is the design's own extension.
- "**The device registry row is what an AERB licence points at.** A machine that does not exist as a resource cannot be licensed" (`origin/main:docs/runbooks/radiology-go-live.md:134-136`). The per-device licence inventory is R-256 (`00-OWNER-RULINGS-REGISTER.md:268`, vendor-fact, pre-plan-authoring) — a fact only the owner produces. A seeded `MMG-1` on production with no mammography unit either sits RED in `radiology_devices_licensed` for ever or gets a certificate row filed against a machine that does not exist — a false entry in a radiation-safety register (law).
- The census flips on fiction: `radiology_device_present` = `listResourcesOfKind(db,"device").length > 0` (`origin/main:apps/core/scripts/standup-check.ts:635-636`), and HO E1's degraded-window logic keys on "a device exists" (`2026-09-06-HANDOFF-commissioning-lane-11i.md:256`), which edge 4 relies on. After E5-M1 the census says "device present" and the window question is asked for machines nobody has.
- What the seed may legitimately do on production is ruled: services with no prices and the self-published `study_types` v1 (owner ruling 2026-08-31, `seed-radiology.ts:24-36`; RAD `:59-63`); the re-run is safe for the book (`:170-205`).

**Amend.** DECIDED 5 → "services + the ruled `study_types` book by the deploy; **devices from the owner's inventory (R-256)** — `MODALITY_MACHINES` read from a `radiology-devices.json` the RSO supplies (or `SEED_RADIOLOGY_DEVICES`), never the constant on a prod target". E5-M1's acceptance drops `radiology_device_present`; it moves to E5-M4 beside the certificates. RAD §5's "add it to `MODALITY_MACHINES` and re-run" is the same gap and is amended with it.

## R4 — AMEND (money marked DECIDED): DECIDED 12 fixes the panel counter's BEHAVIOUR, not just its sentence

**Claim.** "The panel/TPA line … is the corporate-standard one — 'the panel rate is the price; ₹X is payable' … the standing rule closes it, not a new ruling."
