## R1 — KILL (the parameter; replace it) · E1-M2 acceptance "`check-config-present` refuses a base without `opd_config.baseline`" + §4 row 21

**Claim in the design.** E1-M2: "`check-config-present` refuses a base without `opd_config.baseline` (`check-config-present.ts` shape)". §4 row 21: "deploy-dark (RM rule 4): consult inert without config; `check-config-present` names the key; `seed:opd` writes defaults on the same deploy".

**Why it cannot stand.**
1. `seed:opd` cannot write anything to an existing production row. `apps/core/scripts/seed-opd.ts:17-21`: `db.insert(opdConfig).values({ … dangerRanges: DEFAULT_DANGER_RANGES … }).onConflictDoNothing()` and the log line `"opd_config exists — left untouched"`. `danger_ranges` is ONE jsonb column (`kernel/db/schema/opd.ts:29`). Production has held `opd_config 'main'` since its first deploy (`docker/prod/deploy.sh:538` "seed:opd … onConflictDoNothing"). A new `baseline` key inside `DEFAULT_DANGER_RANGES` therefore never reaches production through the seed.
2. `check-config-present` is the deploy's HARD gate, after migrations and before the images come up. `docker/prod/deploy.sh:40 set -euo pipefail`; steps: migrations `:506`, cursor seeding `:513`, configuration seeding `:523-612`, `seed-roles` non-fatal `:626-629`, **"configuration gate — refuse to continue" `:635`, `check-config-present.js` `:645`**, "6/8 api, worker and caddy up" `:673`. Its own header (`apps/core/scripts/check-config-present.ts:15-27`) says why it must not demand what the owner has not typed: "Wiring that verdict to deploy.sh's exit status would make EVERY deploy fail … which is not a gate — it is a broken deploy."
   So the weekly tip that carries E1-M2 migrates production, leaves `opd_config` untouched, refuses at the gate, and never brings the api up. That is the 2026-09-06 accident's shape with a different cause.
3. Worse if the zod schema is tightened: `loadOpdConfig` `safeParse`s `danger_ranges` on every call and throws `opd_config_invalid` (`modules/opd/config.ts:180-181`). A REQUIRED `baseline` key stops every consult and every vitals write on production at once.
4. The design contradicts itself: DECIDED 9 "unreadable table or absent config → band behaviour"; §0 "inert while `opd_config.baseline` constants are absent". RM §3 rule 4 (`:378-381`) says inert-until-configured OR config one deploy earlier; RM §3 rule 5 (`:382-386`) says a false row that needs configuration nobody has created is a **must-not-open-without census row**, never a deploy refusal. E1-M2 already names that row (`vitals_baseline_config_present`) — the `check-config-present` refusal is a second, wrong instrument for the same fact.

**Replace with.** `baseline` OPTIONAL in `dangerRangesSchema`; `boardFlags` inert when absent (DECIDED 9); `vitals_baseline_config_present` is the G2 census row (RED with the fix text naming `PATCH /opd/config` — `updateOpdConfig`, `config.ts:244-252`, is the only writer an existing production has); the phase doc states which of RM rule 4's two choices it took. Row 21's expected behaviour becomes "census RED, consult inert, deploy proceeds, api up". Note that the restore-drill rehearsal (RM Q3 `:264-265`, "seeds and gate included") would have CAUGHT this tip before a window — the design has no drill row; see R12(c).
