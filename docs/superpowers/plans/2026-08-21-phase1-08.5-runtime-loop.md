## Design (the decisions this plan makes — read before the tasks)

### D1. Two processes, one build: a `WorkerModule`, not a headless `AppModule` *(FORK-A, spike question A)*

`apps/core/src/worker.ts` boots `NestFactory.createApplicationContext(WorkerModule)` from the
same build (`start:worker` script, same `loadConfig()`). **Default branch — WorkerModule:** a
providers-only module (CONFIG · DB_BUNDLE → DB/DB_POOL · MODULE_REGISTRY with the same seven
manifests + the alerts manifest · the Scheduler) with no controllers, **no `RealtimeModule`** —
so the worker structurally cannot start the tail or the WS server (roadmap trap 2). The refuted
branch — reusing `AppModule` — is expected to die at boot: `RealtimeGateway.onApplicationBootstrap`
calls `this.adapterHost.httpAdapter.getHttpServer()` (`gateway.ts:71`) and an application context
has no HTTP adapter. **Decision rule: if the spike shows AppModule boots headless AND cleanly
skips the gateway, a plan amendment may adopt it; absent that measurement, WorkerModule ships.**
The worker owns its pool and closes it once on shutdown (the `app.module.ts` double-close guard
pattern). Dev compose unchanged; the production compose service, restart policy and alerting on
the heartbeat are Plan 11's.

### D2. The scheduler: advisory-lock interval loop by DEFAULT; pg-boss as the designed alternative *(FORK-B, spike question B)*

**This inverts the roadmap's ordering of the two branches, for a reason the spike must confirm:**
the dispatch cycle needs a 1–2 s cadence, and pg-boss's cron scheduling is minute-granular —
driving a 1–2 s job through pg-boss means self-rescheduling singleton jobs (`sendAfter` chains)
for exactly the job that matters most, which is complexity without benefit. The advisory-lock
loop gives 1–2 s cadence natively, adds **no dependency, no second migration system, no harness
risk**, and spec §2 v4.3's "coordination stays in Postgres" is satisfied either way. The roadmap
itself blesses the loop ("Plan 11 may still move it onto pg-boss").

- **Default branch (the loop):** a `Scheduler` registering jobs of two kinds — `every(ms)` and
  `dailyIST("HH:mm")`. One `unref()`'d `setInterval` per `every` job; one 30 s ticker for the
  daily jobs. Each tick, on ONE checked-out client: `pg_try_advisory_lock(hashtext('job:<name>'))`
  → if won: write `scheduler_heartbeats.last_started_at`, run `run(now)`, write
  `last_ok_at`/`last_duration_ms` (or `last_error` + append `sweep.failed`), then
  `pg_advisory_unlock` and release the client. The loser of the lock skips the tick silently —
  singleton and multi-process-safe by construction. Per-job re-entrancy guard in-process (the
  tail's `polling` pattern) so a slow run is never overlapped by its own next tick. Daily jobs
  fire on the first ticker tick where `now` is past today's IST instant AND
  `istDay(heartbeat.last_ok_at) < istDay(now)` — the heartbeat row doubles as the daily-run
  memory; a failed daily job retries on the next tick until it succeeds.
- **Alternative branch (pg-boss):** `pg-boss` dependency + its own `pgboss` schema beside
  drizzle's; cron registration for the daily jobs; a self-rescheduling singleton job for
  dispatch/timers; `start()`/`stop()` in the worker lifecycle; T2's tier becomes CRITICAL
  (migration/harness interplay) and its brief gains the §6 rollback questions for the pgboss
  schema. **Decision rule (verbatim from the prompt, binding): if pg-boss needs ANY change to
  `jest.config` or `test/helpers/db.ts` to coexist with the suite, take the advisory-lock loop.**
  The spike additionally reports the fastest achievable recurrence; if pg-boss cannot drive a
  1–2 s dispatch without a `sendAfter` chain, take the loop.

### D3. The lock is noise-reduction — correctness NEVER rests on it

Every one of the six sweeps is already idempotent and multi-process-safe by its own claim
(`runDueTimers` claims each timer with conditional `UPDATE…RETURNING`; `runDailyClose` claims the
day with `INSERT … ON CONFLICT DO NOTHING`; the others are conditional-update sweeps). A
double-fired sweep does duplicate WORK, never duplicate EFFECT. Therefore **this plan writes no
test that claims to observe the advisory lock** — that is §3.21's entire defect class (four
specimens), and here even a lock-less mutant changes no observable effect. The lock's job is to
keep two workers from burning the same cycles; the sweeps' own tests (already shipped) carry the
correctness. Stated here so no gate demands a lock-observation test and no coder writes one.

### D4. Dispatcher correctness: look-back window + per-consumer delivery claims, **claim recorded on SUCCESS**

The shipped `runDispatchCycle` reads `seq > last_seq` and advances the cursor — so a row whose
`seq` was allocated early but committed late is skipped forever (the window `tail.ts:15-24` names
and defends; `dispatcher.ts:21-27` does not). The fix is the tail's approach made durable:

- **Read a window, not a frontier:** `seq > GREATEST(cursor − lookback, 0)` (lookback default
  500, calibrated by spike C), LEFT-JOINed against `event_deliveries` so already-resolved rows
  drop out. The query stays one WHERE chain so Plan 11's partition floor
  (`recorded_at >= floor`) is **one added predicate** (roadmap trap 8).
- **`event_deliveries(consumer, seq)` PK** with `status` (`retrying` | `done` | `parked`),
  `attempts`, `last_error`, `next_attempt_at`, `updated_at`. The claim row is written
  `status='done'` via `INSERT … ON CONFLICT DO UPDATE` **after the handler succeeds**.
- **This is deliberately the OPPOSITE placement from billing's `withIdempotency`** — and the
  contrast is the design decision (§3.49: a decision needs the mutant that inverts it, and this
  plan's Assertion Book row L2 is that mutant). Billing claims BEFORE the work because its
  nightmare is doing the work twice — a second receipt is a real document. The dispatcher's
  nightmare is the mirror image: **losing an event**. A claim taken before the handler that then
  crashes (process death between claim and effect) marks an undelivered event delivered — silent
  loss, the exact defect this plan exists to remove. Claim-on-success gives at-least-once
  delivery with dedupe; the rare double-delivery under a race is absorbed by the consumer's own
  idempotency, which the architecture already mandates (roadmap trap 6). At-least-once +
  idempotent consumers is the contract; it is stated here once and every consumer inherits it.
- **Poison handling:** a handler failure upserts the delivery row (`retrying`, `attempts+1`,
  `last_error`, `next_attempt_at = now + min(2^attempts, 60) s`). While `next_attempt_at` is in
  the future the row is skipped, and an unresolved row HOLDS the cursor (below). At
  `attempts ≥ maxAttempts` (default 5) the row is **parked**: in ONE transaction — dead-letter
  row inserted into `event_dead_letters`, delivery status flipped to `parked` (guarded
  `WHERE status <> 'parked' … RETURNING`, so exactly one transitioning transaction exists), and
  `consumer.poisoned` appended. The cursor then moves on: one permanently failing event no longer
  blocks its consumer forever (the shipped `break` at `dispatcher.ts:34` does exactly that today).
  Requeue/replay tooling for dead letters is NOT built here (D12).
- **Cursor semantics:** after a cycle, `cursor := (min unresolved seq in the batch) − 1`, else
  the max seq seen; never decreased. `event_cursors` keeps its exact shape. The documented
  residual (same as the tail's): a transaction that commits more than `lookback` seqs late is
  still lost — spike C measures how large that window can get in this harness, and the constant
  is set from the measurement, not from taste.
- `runDispatchCycle` gains `now` in its options (backoff arithmetic must be drivable by a test —
  the Global Constraint applied to the dispatcher itself).

### D5. `event_deliveries` and `idempotency_keys` STAY SEPARATE *(ruling the prompt requires)*

Same idea — a uniqueness claim arbitrating "at most once" — but they share no code. Different
lifetimes (request-scoped rows carrying a serialized HTTP response and released on failure vs
permanent per-(consumer, seq) marks that are never released and carry no payload), different
claim placement (before vs after, §D4 — a shared helper would have to parameterize the single
most safety-critical decision either side makes, which is how the wrong placement migrates),
different failure semantics (billing DELETES on failure; the dispatcher COUNTS failures toward
parking). A shared abstraction here would be a name, not a mechanism. Ruled: separate.

### D6. The one consumer: `kernel.alerts`, idempotent per (event, recipient), identity-scoped access, no patient identity anywhere

- **Table:** `alerts(id, user_id → users.id, kind, title, body, ref_type, ref_id,
  source_event_id, created_at, read_at)` with **UNIQUE (source_event_id, user_id)**. The roadmap
  wrote `source_event_id UNIQUE`; that is per-row shorthand and would cap one escalation at ONE
  recipient — a single `escalation.triggered` fans to every id in `resolvedUserIds`, so the
  idempotency unit is the (event, recipient) PAIR. Corrected here deliberately.
- **Consumer:** subscribed to `escalation.triggered` (declared in an `alertsManifest`
  `subscriptions` entry — the §4 seam, finally consumed; spike D confirms the seam is
  declarative-only today so T2's wiring assertion starts from zero). Per recipient, in one
  transaction: `INSERT … ON CONFLICT (source_event_id, user_id) DO NOTHING RETURNING`; only a
  won insert appends `alert.raised` (payload: alertId, userId, kind, refType, refId,
  sourceEventId — the tail fans it to `alerts:<userId>`). `fallbackExhausted: true` ⇒ the
  recipients are every holder of role `owner` (the owner-SMS half stays Plan 10). Redelivery of
  the same event (D4's at-least-once) inserts nothing and appends nothing.
- **No patient identity in any alert column — a §14 public-surface rule with a MUTANT, not a
  comment** (Assertion Book L8; prompt §7). Title is built exclusively from
  `defKey · state · rung`; refs are `workflow_instance`/instanceId; the recipient reaches the
  patient only through permission-checked routes. Note the seam is real: `DispatchedEvent`
  carries `patientId`, so the wrong implementation is one property access away.
- **Access is identity-scoped, NOT permission-gated** — the `/auth/me` precedent (a route with
  neither `@Public` nor `@RequirePermission` is authenticated-only; `PermissionGuard` returns
  true when no requirement is declared). Your alerts are yours by identity, not by role. This
  deliberately avoids minting an `alerts.read` permission that every seeded role would need —
  the exact trap pipeline C carried forward as "the cashier holds no `tariff.read`". Both routes
  refuse agent actors explicitly (agents pass `AuthGuard` on permissionless routes, so the
  refusal must be in the handler: actor.type !== "user" ⇒ 403).
- **Routes:** `GET /alerts` → own alerts, unread first then `created_at` desc, `LIMIT 50`, plus
  `unreadCount` (bounded by construction — the carried-forward unpaginated-route complaint does
  not get a fourth specimen). `POST /alerts/:id/read` → conditional
  `UPDATE … SET read_at = now WHERE id AND user_id AND read_at IS NULL RETURNING`; a won update
  appends `alert.read`; a repeat is a 200 no-op appending nothing; another user's alert id is a
  404 (no existence leak). Naturally idempotent — the route takes no idempotency claim.
- **Realtime:** `TopicSpace` gains an optional `authorize(userId, topic) => boolean`; a space
  declares exactly one of `permission` | `authorize` (validated at registration). The alerts
  space is `{ prefix: "alerts", authorize: (u, t) => t === `alerts:${u}` }` — subscribable only
  by that user. The gateway's subscribe path changes by one branch; the permission path for
  every existing space is byte-identical.
- **`sla.breached` stays record-only** (§10.3: structure everywhere, alerts selective); the
  ladder's rung 0 is the first human-facing moment by design. SLA minutes are definition data —
  tuning 45+15 is an owner call on data, not code.

### D7. Heartbeats and `/health`: `ok` | `stale` | `not_running` — degraded, never down

`scheduler_heartbeats(job PK, last_started_at, last_ok_at, last_error, last_duration_ms)` —
upserted every tick (an UPDATE every 1–2 s; **no per-tick events** — flood). This table's shape
is the §11.19-C fix-29 precedent 12a's agent heartbeats will reuse (`job` = agent name later;
roadmap trap 9). `/health` gains a `worker` field: `not_running` (zero rows — a deployment
without a worker is not a fault the API can diagnose; status stays `ok`), `ok` (freshest
`last_started_at` within `WORKER_STALE_AFTER_MS`, default 60 000 — 2× the slowest *interval*
job's cadence, NOT 2× the daily jobs'), `stale` (older ⇒ status `degraded`, **never `down`** —
the worker is never load-bearing for a human flow, trap 1). The existing `health.e2e` asserts
the old two-field body; T1 widens that assertion in place (a modification, not a deletion).

### D8. New events: `sweep.failed`, `consumer.poisoned`, `alert.raised`, `alert.read`

`kernel/worker/events.ts`: `sweep.failed` (module `worker`; job, error, durationMs) appended by
the scheduler when a run throws; `consumer.poisoned` (module `worker`; consumer, seq, eventId,
error, attempts) appended inside the parking transaction. `kernel/alerts/events.ts`:
`alert.raised`, `alert.read` (module `alerts`; payloads in D6). Four names, `entity.verb_past`,
full envelope via `defineEvent` — catalog additions, no version bumps. No per-tick events.

### D9. Config: zod-defaulted keys, no `.env` edits anywhere

`WORKER_DISPATCH_INTERVAL_MS` 2000 · `WORKER_TIMERS_INTERVAL_MS` 20000 ·
`WORKER_TEMP_ROLES_INTERVAL_MS` 60000 · `WORKER_DAILY_TICK_MS` 30000 ·
`WORKER_STALE_AFTER_MS` 60000. Daily IST times are code constants beside the registration
(`guardians 00:05 · no-shows 23:55 · daily-close 23:59`) — they are design decisions from the
roadmap, not deployment knobs. All keys default in the schema, so no server or CI `.env` changes;
the "hard-fail on missing values" rule is untouched because nothing new is required.

### D10. The dated-bomb fix rides this plan *(prompt §6.2 — a scheduling plan must not ship on a suite that fails on the clock)*

`opd-lifecycle.e2e.test.ts` fails for the last ~30 minutes of every IST day (docs-only commit
`f76f82e` went CI-red on it; ledger §3.41). Root cause: the suite books "today's first slot
> 20 minutes out" against the wall clock, and the day's last bookable slot is 23:50 IST. The
service layer already takes `now` everywhere; only the suite's HTTP path rides the wall clock.
**Fix (T6): pin `Date` — and only `Date` — for the whole suite** via jest's modern fake timers
with a `doNotFake` list that leaves every timer real (pg sockets and supertest keep working),
`setSystemTime` to a fixed mid-day IST instant. The app boots in the same jest process, so the
pin reaches every `new Date()` on both sides of HTTP. **Fail-first is the bomb made
deterministic:** pin 23:46 IST against the unmodified suite and reproduce CI's exact red
(`expect(slot).toBeDefined()`, three legs) on demand — then the fix pins mid-day and adds one
teeth assertion (the `/opd/slots` default date equals the pinned day, proving the pin reached
server code). Mechanism is flag ③ and spike question E; the fallback if the probe fails
(arrange via service calls with explicit `now`, assert over HTTP) is designed but second choice
because the class-4 queue assertions also read the clock server-side.

### D11. `SubmitButton` is an APP convention prospectively; the retrofit is booked, not absorbed *(the ruling the prompt requires)*

Every NEW write surface mounts `SubmitButton` — the bell's mark-read does, passing its minted key

### D12. What this plan deliberately does NOT build (stated, like Plan 08's D10)

No notification channels, templates, quiet hours or matrices (Plan 10 — in-app alerts are not
subject to quiet hours, trap 5). No events-table partitioning and no `recorded_at` floor
predicate (Plan 11 — the query is merely SHAPED for it). No production compose service, restart
policy or heartbeat alerting (Plan 11). No dead-letter requeue/replay tooling and no agent
harness (12a — the heartbeat table is its precedent, nothing more). No second consumer, no
memberships accrual (Plan 09). No `POLL_MS` lift or OPD `SubmitButton` retrofit (booked below).
No Redis, no broker, no second scheduler — Plan 10's outbound queue rides THIS worker (trap 4).
No change to `merge.ts` check-on-execute (trap 1: it stays; the comment is updated by T5 to say
the loop now exists but merge stays check-on-execute BY DESIGN). The tail keeps its `setInterval`
in the API process — it is a different cursor with different guarantees and is never merged with
the dispatcher (trap 2).

## Global Constraints (spec v4.6 + roadmap standing rules + this plan)

1. **The worker is never load-bearing for a human flow.** Nothing a human does blocks on it;
   when it is down, timers accumulate and drain on restart (T6 asserts the drain);
   check-on-execute stays where it is (`merge.ts`).
2. **The tail and the dispatcher are different cursors with different guarantees — never merge
   them; no screen depends on the dispatcher.**
3. **jest runs sweeps directly, never through the scheduler.** The scheduler's own tests drive a
   fake clock over stub jobs; the sweeps keep their shipped tests.
4. No Redis, no broker, no second scheduler. Plan 10's outbound queue rides this worker.
5. Quiet hours and notification matrices are Plan 10's; in-app alerts are exempt by design.
6. The alerts consumer is idempotent per `(source_event_id, user_id)` and **never fans out
   patient identity** (mutant-enforced, L8).
7. The dispatcher's events query stays one WHERE chain so Plan 11's partition floor is one added
   predicate; nothing here pre-empts the partition job.
8. `scheduler_heartbeats` is the fix-29 precedent for 12a's agent heartbeats — same shape.
9. Every clock-reading service takes `now: Date = new Date()` — including the scheduler's job
   contract (`run(now)`), the dispatcher's backoff, and the amended `sweepExpiredTempRoles`.
10. **No timing assertion in this plan gates on a wall-clock mean or median.** Anything timed
    gates on the fastest observation or on an invariant (ledger §3.50; the 2026-08-21 CI perf
    incident). This plan authors NO new perf budget: the five gated budgets are untouched, and
    the worker never runs during jest (constraint 3), so it adds no load to the gated suites.
    The five-minute real-clock transcript in the gate report is a DEMONSTRATION, not a test —
    the deterministic proof of registration is L14.
11. Events: append-only, `entity.verb_past`, full §10.5 envelope; **no per-tick events**.
12. TypeScript strict, no `any` in kernel; module isolation lint holds (kernel/alerts is kernel
    code; it imports no module's tables).
13. Migrations: rollback stated before the generator runs (§6); the full generator output set is
    committed (§3.16); truncate-group rule quoted verbatim in T1 (§3.35).
14. Workspace test totals must not decrease; no test is deleted; the runner's own summary line is
    quoted by exact path (AGENT-RULES §4). **No per-task test-count targets exist in this plan.**
