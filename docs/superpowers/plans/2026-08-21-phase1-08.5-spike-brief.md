## Question A — a Nest application context without HTTP

Prove, by executing both, which boot shape the worker uses:

- **A1 (expected winner):** a new `WorkerModule` — providers only (`CONFIG`, `DB_BUNDLE`→`DB`/
  `DB_POOL`, `MODULE_REGISTRY` with the same manifests), **no controllers, no `RealtimeModule`**
  — booted with `NestFactory.createApplicationContext(WorkerModule)`. Measure: does it boot,
  resolve `DB`, run one `runDueTimers(db, now)` call, and shut down cleanly (`app.close()` ends

  `RealtimeGateway.onApplicationBootstrap` calls
  `this.adapterHost.httpAdapter.getHttpServer()` (`gateway.ts:71`) and an application context has
  no HTTP adapter. Capture the actual error verbatim. If it somehow boots, measure whether the
  tail started (it must not — trap: the worker never runs the tail or the WS server).

Report: the winning shape, the exact provider list WorkerModule needed, the A2 error text, and
anything surprising about `enableShutdownHooks`/`close()` ordering in a context (the pool-end
sequencing that `app.module.ts` documents).

## Question B — the scheduler fork: pg-boss vs the advisory-lock loop

The plan's default is the **advisory-lock interval loop** (plan D2 states why: the dispatch cycle
needs a 1–2 s cadence and pg-boss's cron scheduling is minute-granular, so pg-boss would need
self-rescheduling singleton jobs for the one job that matters most). Your job is to confirm or
refute the facts that default rests on, executing, not reading:

- **B1 — pg-boss under this jest harness.** `pnpm add pg-boss` (spike branch only). In a scratch
  spec: `new PgBoss(workerUrl)`, `start()`, schedule a cron job, `sendAfter` a delayed job,
  observe both fire, `stop()`. Measure: (i) what schema/objects `start()` creates and in which
  database; (ii) whether a second `start()` against the same database (per-suite reset shape) is
  clean; (iii) the fastest recurrence you can achieve for a "run every 1–2 s" job and what it
  costs (cron floor? `sendAfter` chains? a `work()` team polling?); (iv) whether ANY change to
  `jest.config` or `test/helpers/db.ts` was needed to make the suite coexist with it. **(iv) is
  the plan's decision rule: any such change ⇒ the loop branch is taken, unconditionally.**
- **B2 — the loop's lock.** On one checked-out `pg` client: `select pg_try_advisory_lock
  (hashtext('job:runDispatchCycle'))` → run a no-op → `pg_advisory_unlock(...)`. Prove with two
  concurrent clients that exactly one wins while held, the loser returns `false` (never waits),
  and the lock dies with the session (kill client A holding it; client B then acquires). Confirm
  `hashtext` exists in Postgres 16 and returns a stable int4 for the same string within a
  database.

Report: the (iv) verdict with evidence; the B1 measurements; the B2 transcript; a one-line
recommendation for the plan's FORK-B.

## Question C — reproduce the dispatcher's out-of-order-commit skip (the spike's centrepiece)

Against the SHIPPED `runDispatchCycle` (`kernel/events/dispatcher.ts`), in a scratch spec beside
it (never edit the shipped file):

1. Open two raw `pg` clients (not the pool). Client A: `BEGIN`, `INSERT` an event (allocates
   `seq N`), **hold the transaction open**. Client B: `BEGIN`, `INSERT` (allocates `N+1`),
   `COMMIT`.
2. Run one `runDispatchCycle(db, bus)` with a consumer subscribed to that event name, recording
   deliveries. Expect: `N+1` delivered, cursor now `N+1`.
3. Client A: `COMMIT`. Run the cycle again (twice, to be sure).
4. **Assert `N` is never delivered** — that assertion PASSING is the reproduction. Quote the
   delivered-seq list and the `event_cursors` row.

Then measure the window's shape: how large a seq gap can a stalled transaction create in this
harness (batch inserts on B while A holds)? This calibrates the plan's look-back constant
(default 500, the tail's). Also confirm the poison behaviour while you are there: a consumer
whose handler always throws holds its cursor forever (`break` at `dispatcher.ts:34`) and blocks
every later event for that consumer — one cycle transcript suffices.
