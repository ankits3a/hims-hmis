> **The tripwire list now lives in [`reports/EXECUTION-LESSONS.md`](reports/EXECUTION-LESSONS.md) — the pipeline's own defect ledger.** Read that file before compiling any pipeline and paste its **§1 Tripwires block verbatim at the top of every task brief**. Plan 02's pipeline A spent ~465k of 1.26M subagent tokens (37%) on failures that the ledger now prevents.

**Where the build lives.** The **server checkout `/opt/hmis` on `root@62.238.106.231` is canonical for code**; the Windows repo `C:\Users\ankit\hmis` is canonical for docs/plans. Both push to the same private GitHub repo, so **always `git pull` before writing** in either, and rebase the server (`git pull --rebase origin main`) if a docs commit landed while a pipeline was running.

**Two hard environment facts:**
- **The server's deploy key cannot push `.github/workflows/*`** — GitHub refuses it. Any plan touching CI must make that edit in the local repo and push from there (the owner's `gh` token carries the `workflow` scope).
- The server is **shared with an unrelated InsForge stack** (`/opt/InsForge`, `insforge-*` containers, ports 5430/5432/7130/7133). It is not part of this architecture and is off-limits to every agent.

**Brief boilerplate every task needs** (Plan 01's pipelines carry the exact wording): `/opt/hmis` is the only writable path on the server, *including no writes to `/tmp`* · no docker container may be created except the `hmis` compose project · never read, stat or reference `/opt/InsForge` — not even read-only · **the owner may be working on the same host from the same IP and key, so never infer from logs or timestamps who did what, and report only what you yourself did** · guard any `apt` with `NEEDRESTART_MODE=l` so it cannot bounce the shared docker daemon.

**Acceptance-criteria discipline (the expensive lesson).** Every criterion must be **attributable to the task itself**. A criterion asserting the state of anything the task does not control — a co-tenant stack's health, another actor's files — cannot be satisfied by correct work, and the retry ladder will burn three attempts and halt the chain. Plan 01's first pipeline died exactly this way.

**Verify-by-execution.** Three defects in Plan 01's "exact" code passed typecheck and failed only at runtime: a lint matcher that matched nothing, a SQL array parameter that didn't bind, a CI action input that hard-errored. **Hand-written matcher patterns, raw-SQL parameter binding, and third-party CI action inputs must be proven by running them** — and a CI task is not done until a run is observed green.

**Pipeline shape that worked:** ≤6 tasks per Workflow, strictly sequential waves when tasks share files, sonnet coders with an Opus gate per task, retry → escalate to heavy-coder. Expect ~700k–1M subagent tokens and 60–90 min per 5-task pipeline. Tell each brief which *existing deviations not to "fix"* — gates otherwise fail work for touching them, and coders otherwise revert them.

## Open architectural decisions (not yet resolved — resolve before go-live)

**Event-log partitioning (spec §11.18 sweep #10) — half resolved.** The idempotency half is **DONE**: the owner chose the side-table option on 2026-08-12, and `event_idempotency` now holds the global uniqueness (commit `3660ffa`, gate report §3). `events` therefore has **no unique constraint that a partition key would fight** — the blocker is gone, and it was executed while the table had zero rows.

**RESOLVED 2026-08-12 (owner delegated the call in-conversation): hybrid — partition `events` by `recorded_at`, monthly, and give the dispatcher a pruning floor.** Rationale: spec §11.18 sweep #10 is design law and demands *monthly* partitioning aligned to retention/archival — only `recorded_at` satisfies that (it is always `now()` at insert, so every insert lands in the newest partition; `occurred_at` can be backdated by downtime backfill and would scatter inserts across closed partitions). The dispatcher objection is closed by the hybrid: `runDispatchCycle` gains a `recorded_at >= floor` predicate where floor = `date_trunc('month', recorded_at-of-cursor-seq)` — `seq` and `recorded_at` are not perfectly monotone together (`recorded_at` is transaction-start time), but month truncation absorbs any transaction-length skew, and pruning to "cursor's month onward" is the entire win. `seq`-range partitioning was rejected because it cannot drop/archive by calendar month, which is the retention unit the spec fixes.
**Implementation home: Plan 11** (the conversion is a table-recreate migration; the monthly partition-creation job needs pg-boss, which Plan 11 schedules; retention/archival is ops scope). Deliberately not earlier: production rows only exist after go-live, so the conversion stays cheap through Plan 10, and no interface changes leak into Plans 02–10 (`appendEvent` unchanged; `runDispatchCycle` only gains the floor predicate). Plan 11 must ship: partitioned recreate (PK becomes `(seq, recorded_at)`; the `event_id` unique index becomes `(event_id, recorded_at)` — harmless, ULIDs are unique by construction and semantic dedup already lives in the non-partitioned `event_idempotency`), a DEFAULT partition + several months pre-created, the pg-boss monthly creation job, the dispatcher floor, and retention/archival honoring legal holds.

**Deployment topology (Plan 11).** `62.238.106.231` is currently build host, InsForge co-tenant, and prospective deploy target simultaneously. Spec §12 wants primary and standby in **different fire zones**. Needs a real decision, not a default.

**Config & secrets ownership — RESOLVED 2026-08-12 (owner chose in-conversation):** env-file pattern. Secrets live in `apps/core/.env` (git-ignored, chmod 600 on the server), loaded natively by Node 22 (`util.parseEnv`, existing environment always wins) through a zod-validated `loadConfig()` in the kernel that **hard-fails on missing values — no fallbacks anywhere**. DB-held secrets (TOTP seeds) are additionally sealed with AES-256-GCM under a 32-byte `SECRET_KEY` from that file, so dumps/backups never contain raw seeds even before Plan 11's pgBackRest/LUKS encryption lands. `SECRET_KEY` joins the continuity-kit escrow (spec E-2); production key generation + escrow ceremony is a Plan 11 runbook item. Plan 02 implements the loader and retires every hardcoded connection-string fallback. Owner also approved pulling the kernel HMAC signing utility forward from Plan 05 into Plan 02 (badge fast-switch tokens need it; Plan 05's signed QR consumes the same utility).

**Headline: the harvest is mostly confirmatory.** The spec is broader and deeper than the legacy system nearly everywhere — casualty, MLC, corporate/panel, room rent, gate pass, GRN, indent, commission, packages, blood bank, ambulance, diet, death certificate and duty roster are all already in scope, and the deposit machinery (per-bed-class schedule, 75/90% top-up alerts, E7 exhaustion ladder, final bill = charges − deposit − returns) is strictly richer than the legacy IPD Advance screen. **What the legacy system genuinely encodes that we do not.** These are counter-level *rules and interlocks*, not modules — the grain at which a module list cannot help, and the grain at which a missed requirement forces a re-plan.

### Plan 08 candidates (billing counter) — RESOLVED 2026-08-18: all three ruled, folded into the written Plan 08 (see its roadmap entry above)

1. **The dues / credit-bill lifecycle — nothing in spec or roadmap.** Zero hits for `dues`, `partial payment`, `part payment` across both documents. The legacy counter saves every bill into one of four states — **paid / dues / discount / paid+discount** — and carries a dedicated *Dues Clear* screen supporting **partial** settlement against one bill plus discount-at-clearance. Our model is pay-before-consult for OPD and deposit-then-settle for IPD; neither describes an outstanding receivable held at the counter. Real hospitals carry dues. **Ruling needed: may a bill be issued unpaid, and if so what is its lifecycle, who may clear it, and what approval does a discount-at-clearance require (Plan 04 consumer)?**
2. **Patient advance as a ledger instrument, distinct from deposit policy.** We specify *how much* deposit to demand and when to alert; we do not specify the instrument — zero hits for running balance / patient ledger / carry-forward. Legacy supports multiple advance receipts per patient, a view of saved advances, and an **OPD-taken advance flowing automatically into a later IPD final bill** (cross-episode carry-forward). Sibling open item already on file: `reports/plan-06-stress-test-findings.md:213` flags *"advance receipts ride the same IPD deferral"* as needing an owner ruling before Plan 08 — resolve both together.
3. **Refund guard rules.** Plan 08 already has credit notes, approval-gated vouchers and refund-to-payer. Legacy adds four guards we do not state: a refund **inherits the original bill's state** (a dues or discounted bill refunds in the same condition); **no refund after discharge**; **no pathology refund once the result is saved**; and refund reason **typed as mistake vs genuine** (a reporting dimension, not free text).

### Phase-2 notes (park against the owning module)

- **Pharmacy/inventory:** expired stock blocked from sale and surfaced in red; **strip-vs-piece purchase concept (1×1 vs 1×15) as a first-class packing unit** — an Indian pharmacy data-model requirement, not a display choice; central-store → counter transfer requiring an explicit receipt confirmation at the counter; automatic expiry email one month ahead.
- **Lab/LIMS:** formula-derived results; **sex- and age-based reference ranges**; per-test remarks; automatic abnormal-value highlighting; report print blocked while the bill is unpaid; signature/degree block on the report.
- **Radiology:** doctor-wise report templates authored as editable documents.
- **Owner-facing:** automatic daily SMS/email of total collection (hospital **+** pharmacy) to the owner. The owner used this daily for 15 years; it belongs in Plan 10's notification catalog.
- **Unverified:** birth-certificate issuance to the municipal registrar. Birth is covered as a domain (`birth.recorded`, mother-baby pairing, delivery register, stillbirth vs live-birth at spec:204/256/448) but the certificate flow is not visibly stated the way the death certificate is (spec:154). Check before Phase-2 maternity.
