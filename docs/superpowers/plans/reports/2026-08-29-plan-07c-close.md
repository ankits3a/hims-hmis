## 3. Ground truth, re-measured — and it was worse than §2 recorded

The phase document said there were no indexes on the actor columns. Measured on the dev database at
kickoff, that was true and incomplete:

- **Zero** indexes on `created_by`, `opened_by`, `recorded_by`, `booked_by`, `issued_by`,
  `received_by`, alone or paired with a date, across all eight tables. As documented.
- **`receipt_tenders` carried ONLY its primary key** — not even an index on `receipt_id`, its own
  foreign key, which is what `dayBook` joins on.
- **`receipts` had no index on `service_day` either.** The document did not record this and it is
  the most consequential of the three: **the day book — the screen a cashier closes a shift
  against — has been a sequential scan of every receipt ever taken, since the day it shipped.**

Migration `0041` adds one table and NINE indexes. Two of them are not about briefs at all.

**Measured before/after**, 400,000 synthetic rows, one psql session, the index dropped inside a
transaction that was rolled back so the query shape is identical:

```
WITH  patients_created_by_at_idx:  Bitmap Index Scan       168 buffers    2.019 ms
WITHOUT it (the state before 0041): Parallel Seq Scan   14,544 buffers   47.668 ms
```

## 5. Findings — the ones worth carrying forward

**The drift clause flattered every reader, and a test I expected to pass found it.**
A quarter is 91 days and a half is 183 — both ODD. The first implementation split the window at
`floor(n/2)` and compared `slice(0, half)` against `slice(half)`, giving the second half one more
day than the first. Three visits a day for ninety-one days, the flattest input there is, reported
"up". Silent, systematic, and in the direction nobody questions. Both odd windows are now pinned.

**Two fields, not one: `actor` selects, `reader` aliases.** A supervisor's drill reads the CLERK's
rows and must alias them to the SUPERVISOR's clearance. Collapsing those into one actor hands the
supervisor the clerk's confidentiality clearance — and it is invisible in every test where one
person plays both roles. The mutant printed a sealed patient's real name. `reader` is REQUIRED, not
optional, so the typechecker announced all eleven call sites.

**A2's mutant could not be built, and that is stronger than building one.** The Assertion Book asks
for "append instead of claim → every retry doubles a person's day". `(user_id, day)` is the PRIMARY
KEY, so an appending implementation does not double a day — it errors. Writing that mutant and
watching it fail for the wrong reason would have proved nothing (rule 21). The property is evidenced
where it lives: a test asks Postgres for the second row and reads the refusal.

**The job census lives in FIVE places and `jobs.ts` said three.** `grep "toHaveLength(12)"` finds
two; `scheduler.test.ts` and `worker-runtime.e2e.test.ts` express it as a NAMED ARRAY with no count
to grep for, and the first needs a spy and a daily instant in its clock walk as well. Both were
missed and both were caught by a verify going red. The comment now enumerates all five.

**`user_day_facts` was not in `truncateAll`, and a suite caught it.** A stale row in a CACHE is
nastier than ordinary leftover test data: it does not look like debris, it looks like an answer.

**A latent 500.** `desk.controller.ts` called `deskQuery.parse()` directly, so a malformed `date`
answered 500 rather than 400 — an outage where a caller sent a bad parameter.

**The known wedge flake is fixed, not absorbed.** It cost one full verify run in this session. The
clock is now driven in the test (5 ms per character); the component still reads the real clock,
because reading the real clock is correct behaviour for a scanner detector.

**A host OOM is not a test failure.** The first T4 verify came back exit 1 with 2,468/2,468 tests
passing and one suite that never ran (`SIGKILL`). `dmesg` named the pid at 06:21:20 with grafana
invoking the oom-killer. The suite passed isolated and the full run was paid for again rather than
the red being explained away.

## 6. Two things a reviewer should look at first

1. **The rollup's window seam** (`kernel/desk/rollup.ts`, `factsForWindow`). A day strictly before
   `today` comes from `user_day_facts`; `today` is computed live. A1 holds because `liveFactsFor` is
   the only arithmetic and the rollup is a cache of it — but that is one line, and it is the line
   where a cached total and a live total would start disagreeing.
2. **The reconciliation surface.** For every threshold or sum on the money path: the per-cashier
   split is summed from receipts filtered on `service_day` AND `received_by`, minus
   entered-in-error. Name a real transaction whose money that sum does not include. The obvious
   candidate is a receipt whose `service_day` disagrees with its `received_at` across the IST
   midnight boundary — both readers use `service_day`, so they agree with each other, and the
   question is whether they agree with the DRAWER.

**Not measured, and it should be:** the rollup was never run against a seeded six-month dataset.
A1 is proven over a three-day window. The arithmetic does not change with length, but the
*performance* claim in DD13 is an inference from the index measurement rather than an observation of
the job at scale.
