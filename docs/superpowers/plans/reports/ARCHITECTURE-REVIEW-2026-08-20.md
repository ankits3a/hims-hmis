## 3. Ruling on C1–C8

**C1 — "audit log, not event-driven." CONFIRMED, with one correction.** The dispatcher/subscription half is inert: `runDispatchCycle` has no production caller; `SubscriptionBus.on` is called only in `dispatcher.test.ts`; and the modules know it — `patients/merge.ts:86-89` explicitly chose check-on-execute *because* "a subscription would never tick in production." But the realtime tail is a genuine, production, multi-process-safe consumer, and it is **better engineered than the dispatcher**: `tail.ts:15-24` documents an out-of-order-commit window (a row whose `seq` was allocated earlier but committed later) and defends it with a look-back window and a dedupe set, while noting that **`dispatcher.ts` does not** — `dispatcher.ts:21-27` reads `seq > lastSeq` and advances the cursor, so under concurrent appends a late-committing row is skipped forever. Correct headline: *events are written, screens refresh, and nothing else happens — timers don't fire, sweeps don't run, no one off-screen is told.*

**C2 — breaches recorded, never escalated. CONFIRMED, and it is worse than stated.** `runDueTimers` (`timers.ts:85`) is the only thing that appends `sla.breached` and climbs ladders; unscheduled, the OPD `waiting` SLA (45 min, active, supervisor@15/duty-manager@30 — `opd/workflow-def.ts:22`) and every approval's closure SLA are rows that never mature. And **running the loop alone does not put a breach on a phone**: `escalation.triggered` carries `resolvedUserIds` and nothing delivers it — `timers.ts:150` and `workflow/events.ts:45` defer delivery to Plan 10. So R2 needs one delivery surface (§8). On `vitals.danger_flagged`: it *does* reach the doctor — class-0 queue priority and the `queue:`/`encounter:` topics — so the claim is accurate only as "reaches no one not at a screen," which at 100 OPD/day is adequate and at IPD scale (per-shift vitals, §11.2) is not.

**C3 — the ordering mistake. PARTLY.** What is right: Plan 12's agents are designed as "subscription consumers + scheduled jobs" (roadmap, Plan 12 scope), so 12 structurally depends on the worker; and a ~200-line worker is bundled into Plan 11 with semi-sync replication, fencing, LUKS, pgBackRest, the watchdog box, downtime kits and the events-table partitioning — the plan most likely to stall on hardware and on the still-open topology decision (roadmap: "needs a real decision, not a default"). The cheap part is gated behind the expensive part; unbundle it. What is overstated: the roadmap already allows "11 can start any time after 01"; the deferral was deliberate; and "Plan 12 is where agents go to be postponed" is a prediction about an owner who has shipped seven plans in ten days. Rule: **unbundle and pull the worker forward — yes; "mistake" — no.**

**C4 — no state model. PARTLY, and the evidence cuts both ways.** The audit missed that **journey state already has a uniform, transactionally-consistent home**: `workflow_instances` (def_key, current_state, state_entered_at, subject, patient, encounter) — OPD mirrors it (`opd_encounters.status` is documented as "the read model," `schema/opd.ts:178`). Any flow that runs on the engine contributes journey state by construction; an event-fed *journey* projection would be a worse, eventually-consistent duplicate. What the audit under-stated: **resource state has no home, and module-privatisation has already begun** — `opd_rooms`, `opd_doctors`, `opd_doctor_schedules`, `opd_doctor_leaves` are OPD-private tables for rooms and doctor availability that OT, IPD rounds and the S10 roster will all need. The failure predicted for IPD has happened in Plan 07. And inside Phase 1, billing's SLA-bearing lifecycles (cashier session `open→closing→closed`, refund voucher `issued→paid`, recon) are status columns, not instances — the first drift from §10.2 "every flow is a workflow definition." The remedy is therefore not R4 as written (§4).

**C5 — verdict. CONFIRMED.** The substrate is real and in places under-credited: approvals run as workflow instances with active ladders; single-winner transitions (`instances.ts:108-124`); timers claimed by conditional `UPDATE…RETURNING` in their own transaction (`timers.ts:94-101`); six billing tables immutable by trigger (README, migration 0012); an agent can authenticate and be killed today (`guards.ts:31-36`) and can do nothing else (`guards.ts:71-73`, `instances.ts:99-100`). It is running as one HTTP process with a WebSocket and no jobs. "Conventional application" is exact.

**C6 — 30/72. PARTLY — the spread is the right finding; the composition is off.** See §7.

**C7 — throughput risk > architecture risk. PARTLY.** The risk is real and **already being managed**: METHOD-REVIEW measured it, v2 was adopted the day before the audit, and the owner's own TOKEN-FINDINGS found the 113k pre-read. The audit missed both documents, so R7(e) recommends what is already policy. Two specific corrections: (i) "OPD received a larger plan than billing" is true by bytes (344 KB vs 144 KB) but both are 16 tasks, OPD carried twelve tables + six screens + perf budgets and billing's screens are a separate pipeline — not evidence of misallocation; (ii) METHOD-REVIEW measured briefs at **4.6%** of pipeline cost — "shrinking the plan is not the lever"; coder *turns* (108 tool calls per coder) are. The honest statement: **the calendar will not kill this project (seven plans in ten days); the verification ratchet and the token budget might, and the owner already has the right tool in hand** — the remaining discipline is to prune the ledger on the rule in METHOD-REVIEW §5.6 and never let the ratchet regrow.

**C8 — stop benchmarking SuperOS. CONFIRMED** on reasoning: one launch article with no data model, no autonomy boundaries and beta-labelled clinical features is not steering signal for a two-year roadmap. Article contents: UNKNOWN, and deliberately left so.

## 4. Ruling on the counterarguments

1. **"The loop deferral is correct — YAGNI." Fails.** It was correct on 12 Aug with zero modules. Today six sweeps, every OPD visit's SLA, every approval's closure SLA, the daily close, no-shows and guardian majority are silently not running, and Plan 11 is not "weeks away" in the current order — it is the hardware-gated plan. What survives of the argument: don't build *consumers* speculatively. Ship the worker, the six sweeps, and **one** consumer.
2. **"The projection is premature abstraction." Holds for journey state, fails for resource state.** Journey state: do not build — `workflow_instances` already is it; enforce that flows run on the engine. Resource state: the shape is already fully designed — §11.18 floor → ward/hall → room → bed, bed classes, gender-segregation and isolation constraints, census derivation, quota classes — there is no "we don't know the shape" problem for beds, and OPD has already privatised rooms. What it changes: R4 becomes a **resource registry**, not a projection (§8).
3. **"Two agents early is a distraction from go-live." Partly holds.** §17 step 1 go-live scope is Registration/OPD/Billing **with WhatsApp/SMS confirmations** — Plan 10 is go-live-critical, Plan 11 is the go-live gate, agents are not. So 12a belongs **after** 11, not before it (where the audit put it). 08.5 is the exception: it makes go-live safer at today's scale and is the first thing that looks like an agent (the SLA Chaser *is* `runDueTimers` + delivery).
4. **"Design-heavy is correct for this builder." Holds.** The spec is the durable memory; the plans are what agents type from (LESSONS §5: "briefs that point at the committed plan… no transcription drift in twelve tasks"); the briefs are 4.6% of cost. Lowering *fidelity* is wrong; lowering *uniformity of verification* is right and already done (v2 tiers). Strike "tier plan fidelity" from R7(e); keep "tier verification."
5. **"30/100 is unfair." Partly holds.** As an "are we on track" gauge, scoring 7/12 Phase-1 plans of a 10-stage rollout against a full-hospital bar is misleading — 30 at this point is *ahead* of pace. As a measure of the design-to-build gap it is the correct use. Keep the number, drop the alarm.
6. **"Clinical content is under-weighted." Holds — the most important one.** §11.8 assumes drug–drug and contraindication hard-stops, duplicate-therapy warnings, pediatric dose ranges, formulary, AMS rules; §11.19-D fix 31 assumes ICD-10 capture; §11.18 assumes IDSP/IHIP notifiable lists. **None names a source, licence or budget line**, and §9 buy-vs-build lists the PBX, Tally and HR — not a drug database or a terminology service. This is procurement and clinical governance with lead time, it gates pharmacy (stage 2) and every T2 clinical drafter, and it cannot be built by a pipeline. It belongs on the owner's decision list this week (§8), not inside a medication row.
7. **"Agents-as-cron is the whole roster." Partly holds — and it sharpens the thesis rather than dropping it.** Of the 15 rostered agents, nine should be deterministic automations wearing the agent harness (actor identity, kill switch, heartbeat, mode-awareness — fixes 27–29): **SLA Chaser** (it is the escalation ladder), **Expiry Watchman**, **Recall & Follow-up** (ladder rules; wording is templates), **Leakage Auditor** (SQL — the orphan scan already exists in `runDailyClose`), **Fraud Sentinel** (rules first; a model only as second-stage triage), **Payout Batcher**, **Coverage Resolver** (constraint rules), **Replenishment Agent** (par-level arithmetic), **Turnover Dispatcher** (queue dispatch). Six are genuinely model-backed: Digest Writer, Ops Copilot, Discharge Summary Drafter, Radiology Report Drafter, Claims Drafter, Workflow Tuner — four of them clinical/financial drafters capped at T2. The agentic claim therefore rests on (a) the T2 drafters and the Tuner and (b) the **runtime governance** — and that is precisely what an operating system does: schedule, supervise and govern jobs, a few of which are model-backed. Rename the roster (automations vs agents); don't drop the framing.

## 5. What the audit missed

1. **The dispatcher has a documented correctness hole** (`tail.ts:18-20` names it; `dispatcher.ts:21-27` has it). The first production consumer will silently skip late-committed events under concurrency. 08.5 must fix it before any consumer — a look-back window plus a per-consumer delivery claim (the tail's own approach), proven by a test with a deliberately delayed commit.
2. **pg-boss is not installed and there is no worker process.** 08.5 is the first process split (a Nest application context without HTTP) and the first scheduler dependency; its migrations meet the drizzle harness for the first time — Plan-08-`TRUNCATE`-class surprise territory. Spike it (~50k) before writing the plan.
3. **The loop alone reaches no phone.** Delivery is Plan 10. The cheapest first delivery is **in-app**: an `alerts` table written by the one dispatcher consumer, an `alerts:<userId>` topic router over the existing tail, and a bell in the Shell (the approvals inbox already establishes the pattern). That proves dispatch → write → event → fan-out end to end with no provider procurement.
4. **§10.2 is already being violated inside Phase 1.** Billing's cashier session, refund voucher and recon lifecycles are status columns, not workflow instances. Either retrofit in a hardening round or write the exception down — but add the design rule and a CI assertion: *any SLA-bearing lifecycle runs on the engine*.
5. **Resource privatisation has already happened** (`opd_rooms`, `opd_doctors`, `opd_doctor_schedules`, `opd_doctor_leaves`). The remedy is a kernel resource registry that module tables *reference* (as they reference `patients`), not a projection — and it is needed before **lab and pharmacy** (benches, analyzers, stores are resources), not only before IPD.
6. **Go-live scope includes notifications** (§17 step 1). Plan 10 cannot sit behind 12a.
7. **12a has non-engineering gates with lead time**: the AI-inference-locus decision (cloud under a DPDP processor agreement vs a ₹3–6L on-prem box — §11.19-D fix 44, a §19 pre-go-live gate) and the **DPIA required before each agentic phase** (fix 42). Neither is code. Start them this week or 12a stalls the way 11 will.
8. **Plan 11's events-table partitioning is a table-recreate** and "stays cheap through Plan 10" because production rows don't exist yet. Keep 11 before go-live regardless of anything else in this ruling; 08.5's dispatcher change (a `recorded_at >= floor` predicate later) is additive and does not conflict.
9. **Agent behaviour is being decided ad hoc per module**: `getPatientPhoto` lets agents resolve non-confidential photos (`photos.test.ts:66`) while `getPatient` returns null for agents (`registration.test.ts:164`). 12a must make agent access a grant in one table and sweep the special cases.
10. **No global agent halt.** The kill switch is per agent (`agents.kill_switch`); fixes 27–28 make agents mode-aware; an explicit "all agents paused" flag (one row, one event) is cheap and belongs in 12a's runtime.
11. **"Fail-open" is a guardrail in prose only** — structurally assert it: no controller imports from the agent runtime; every agent-callable is a human-callable API; no human path awaits an agent. Extend the existing module-isolation lint to agent code, and make R9 ("never the database") a lint rule rather than a comment.
12. **Draft provenance is the medico-legal shield and is not specified.** D-36 instruments signer automation-bias; nothing records *what the model produced* versus *what the doctor signed*. Every drafting tool in the 12a tool catalog should stamp model id, prompt version, input hash and draft hash into the event and the signed document, so a discharge summary can later prove what the human changed.
13. **Clinical knowledge sourcing** (§4.6) — a procurement track, unbudgeted, gating stage 2 and every clinical drafter.
14. **The throughput fix is already in force** (METHOD-REVIEW, EXECUTE-METHOD v2, 2026-08-19); the audit's R7(e) should become "prune on the §5.6 rule and never let the ratchet regrow."

## 6. Verdict

**"The direction is correct, but the operating-system layer is missing."** With this refinement: the missing layer is two layers of very different size and one non-layer. The **runtime loop** is small, fully designed (§2 v4.3 process split), largely written, deliberately deferred on 12 Aug, and now overdue — its absence is why the built system is an HIS. The **agent runtime** is large, under-designed relative to the rest of the spec (§16 is a roster plus guardrails; there is no tool-catalog contract, no `InferenceClient` contract, no evaluation or regression harness for model output, no prompt/version governance, no provenance), correctly sequenced after go-live, and gated by decisions only the owner can make. The third gap is not architecture at all — it is **clinical knowledge content**, which a pipeline cannot produce.

The architecture is genuinely OS-shaped: one event spine written in-transaction with causation, flows as governed versioned data, approvals as instances of those flows, timers as rows, agents as first-class actors with a kill switch, and a clinical autonomy cap written into the spec as permanent. That combination is rare. It is also, today, switched off from the neck down.
